## 菜单外链标识统一（UI 约定）

**核心机制（后续新增菜单务必遵守）**：Nuxt UI v4 用 `item.target === '_blank'` 作为「外链」唯一标记，命中后自动在标签后渲染 ↗ 图标（`appConfig.ui.icons.external` = `i-lucide-arrow-up-right`）。

- `UNavigationMenu`（侧边栏、设置页顶部导航）与 `UDropdownMenu`（组织菜单、用户菜单、首页 + 菜单）：带 `target` 即自动出图标。
- `UCommandPalette`（⌘K 命令面板）**没有**这段逻辑，`CommandPaletteItem` 也不支持 trailingIcon，只能在 item 上加 `suffix: '↗'`。
- 走 `onSelect` 手动 `openUrl` 的条目（无 `to`）必须额外补 `target: '_blank'` 才有标识 —— 该字段只用于触发图标，不改变点击行为（条目没有 href，不会真跳转）。

**本次改动文件**：
- `src/components/GroupsMenu.vue`：Create group / Manage groups 补 `target: '_blank'`
- `src/components/UserMenu.vue`：My profile 补 `target: '_blank'`

## 全局搜索（⌘K）关闭后「UI 卡死」排查与自愈修复

**现象**：点侧边栏搜索框打开命令面板 → 点空白处关闭 → 偶发整窗点不动（UI 卡死）。

**排查手段与结论**：
- 用本机 Playwright（Chrome + WebKit 26.5，后者与 Tauri 的 WKWebView 同引擎）搭临时页（真实 default 布局）跑了 40+ 轮时序矩阵（0/20/30/40/60/80/150/250ms 打开延迟、双击、esc、拖拽、退场动画中再次打开、连点 15 次）——**常规路径复现不出真卡死**，说明是竞态而非必现 bug。
- 但用「拦截 CSSStyleDeclaration 的 setter 抓调用栈」拿到了关闭链路上三处全局副作用的真实来源：
  1. `body.style.pointer-events = 'none'`：`reka-ui/DismissableLayer`（按元素 owner）+ `reka-ui/useBodyScrollLock`（Symbol owner）双 owner 引用计数；
  2. `body.style.overflow = 'hidden'` + paddingRight/marginRight + `--scrollbar-width`：`useBodyScrollLock`（由 `DialogOverlayImpl` 调用，**与 `disableOutsidePointerEvents` 无关**，所以 `:content="{ disableOutsidePointerEvents: false }"` 这种官方 workaround 在本项目无效）；
  3. `#app` 的 `aria-hidden`/`data-aria-hidden`/`inert`：`aria-hidden` 包的 `hideOthers`。
- 这三者只在「组件卸载 / present 变 false 的清理回调」里还原。链路一断就永久残留：`pointer-events: none` 沿继承链传遍全页 → 界面在、但点什么都没反应。上游 reka-ui 2.11 之后的分支正在修同类问题（提交原文 "leaving the page frozen"），本项目已是最新版（nuxt/ui 4.12.0 + reka-ui 2.11.0），无版本可升。

**修复**：
- 新增 `src/composables/useOverlayUnlockGuard.ts`：本质是「全局副作用自愈」守卫。弹层 close 后（nextTick + 宏任务）+ 5s 低频巡检，若「body 锁还在但已无任何 `[data-dismissable-layer]` / `role=dialog` / popper 层」→ 就地清掉 pointer-events / overflow / padding / aria 标记，并在 DEV 打一条 warn（这是反查真实泄漏链路的唯一线索）。必须主动巡检：锁生效时页面收不到任何 pointer 事件，被动兜底没机会触发。
- `src/layouts/default.vue`：`UDashboardSearch` 接管 `v-model:open="searchOpen"` 并挂守卫；搜索按钮加 `id="dashboard-search-trigger"`；关闭后等浮层真正卸载再**把焦点还给触发按钮**。
- 焦点归还不是锦上添花：WKWebView 点击 `<button>` 不给焦点，reka 的 `triggerElement` 因此为空，关闭后 `activeElement` 掉到 `<body>`（实测），用户的单键快捷键（n / g h）会全部失灵 —— 这本身就会被感知成「界面死了」。
- 单测 `src/composables/__tests__/useOverlayUnlockGuard.test.ts`（7 例，纯函数判定，node 环境）。

**验证**：WebKit 下生产产物（`vite preview`）连开/关 5 轮，每轮结束后 `body.pointer-events`/`overflow` 清空、`#app` 无 aria-hidden、焦点回到 `#dashboard-search-trigger`；人为注入泄漏（body 双锁 + aria-hidden）后 6s 内被巡检修复且页面恢复可点。typecheck / lint / test(181) / build 全绿。

**顺手清理**：删除临时探针页 `src/pages/dev-search-repro.vue`（上一节记录的那个被截断的调试残留），route-map 已自动回落，不再打进生产路由。

## 分支规范 + CNB 流水线 + Release 发布链路（2026-11-07 晚）
- 交付：`.cnb.yml`(583 行) / `docs/BRANCHING.md`(299) / `docs/design/cnb-pipeline-design.md`(790) / `scripts/ci/` 9 个脚本 / README 加「分支与发布」节 / `.gitignore` 加 `release/`+`out/`。**未 commit 未 push。**
- 用户口径：制品 = 源码包 + macOS 安装包(amd64/arm64) + Windows 安装包(amd64/arm64)；**只有推 `v*` tag 才发 Release**。
- ⚠️ 关键约束（决定了整个架构）：CNB **官方构建节点只有 Linux 容器**（`cnb:arch:amd64` / `arm64:v8`），**没有 macOS/Windows**。打 dmg 需 Xcode、打 exe 需 MSVC → 必须用**根组织自托管 Runner**（`runner.namespace: group` + `tags`，组织设置→构建节点→新增 Runner）。自托管节点不开 Docker → `docker.image`/插件任务/`runner.cpus` 全部无效，只能用宿主机脚本 + curl/PowerShell 调 OPENAPI。
- 流水线设计（4 条 + 2 条注释态）：
  - `ci-pr`（`main.pull_request` 与 `$.pull_request` **双 key + YAML 锚点**复用，`$` 是兜底匹配、与 glob 严格互斥 → 恰好跑一次）：门禁 only
  - `ci-main` / `ci-branch` / `release-meta`（`v*: tag_push`）：门禁 → 版本一致性 → 源码包+Web 包 → 建 Release → 传附件
  - `release-macos` / `release-windows`：**整段注释**，接入自托管节点后取消注释才生效（未接入时会是 v* 失败而非静默降级）
- 门禁顺序是 **install → build → typecheck → lint → test**（`build` 必须在 typecheck 前：干净克隆里 `auto-imports.d.ts`/`components.d.ts` 不存在，`route-map.d.ts` 才入库，反序必红 TS2304/TS2552）
- Release 编排硬规则：**`git:release` 全仓只有 P1 一个调用点**；用 `CNB_TAG_IS_RELEASE` 二选一（false→create 用 `overlying:false`，此时无附件故安全；true→update 用 `overlying:true`，绝不删附件）。`git:release` 默认 `overlying:false` 会**先删后建、清空其他平台已传的附件**，这是最大坑。P2/P3 只传附件、永不建/删 Release。
- 预发布判定：**不能用 `CNB_TAG_IS_PRE_RELEASE`**（它要求 Release 已存在 → 首次创建 rc 时恒 false 会把 rc 当正式版并抢 `latest`）。改用 tag 名是否含 `-` 判定，因此 4 个互斥 job（create/update × 正式/预发布），`if` 必须**单行 + 整体单引号**（不带引号 YAML 会解析失败 → 全流水线失效）。
- 两条"静默不跑 CI"陷阱（都写进文档）：
  1. PR 事件若只挂 `$`，PR 到 main 可能一条都不跑 → 保护分支卡死合并。修法：双 key 并存 + 锚点。
  2. `v*` 是 glob 键、优先级高于 `$` 兜底 → **分支名以 `v` 开头会让该分支 push 完全不跑 CI**。修法：分支命名禁止以 v 开头。
- 首次发版：**A 案**（直接打 `v0.1.0`，不用 rc 试跑）。理由：version-check 严格相等会让 rc 在第 6 stage 就红，恰好跳过最该验的 pack/changelog/release/upload；重试只用平台「重新构建」，**不要删 tag 重打**（会搞脏 changelog 区间基线）。
- 平台侧需人工做：仓库设置→分支保护（新建 main 规则）；设置→云原生构建→允许事件自动触发；根组织→组织设置→构建节点接入 Mac/Windows。
- 过程教训（跨项目通用）：
  1. **复核期间上游还在改文件 → 两个人的结论都对却互相矛盾**。报文件状态一律带 `sha256`/`mtime`；本轮出现 4 次"旧快照判 FAIL"，全部靠哈希定案。
  2. **文档会指挥人把已修的缺陷改回去**（设计稿 checklist 写"可按 R3 删掉冗余那份"，而 R3 写"不得优化掉"）。检查清单与约束条款必须同源。
  3. **门禁脚本的"未实测"部分要显式标注**，不要写得像已验证（P2/P3 至今没在真实自托管节点上跑过）。
