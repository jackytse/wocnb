# 2026-11-12 构建通知点击直达（software-build-notify-click 团队）

## 需求与背景
- 用户提出「流水线监控 + 完成后本地通知」，调查发现**功能已在项目里完整实现**（useCnbBuildWatch.ts 1192 行 + main.ts 接线 + 通知面板 + 设置卡片 + 三语 i18n，63 测试绿）。真实缺口是「系统通知不可点击」。
- 用户选择：先验证能用 + 实现「点击通知直达构建详情」。

## macOS 通知链路的源码事实（QA + 主理人逐行核实，勿再推翻）
- tauri-plugin-notification 2.7.0 → notify-rust 4.18.2，macOS **默认走 NSUserNotificationCenter 旧后端**；UN 后端需 `preview-macos-un` feature，**插件未暴露**（Cargo.toml 只有 win7 系 features）。lib.rs 原注释「macOS 走 UN」是错的，已修正。
- 通知显示兜底：`notification.show()` 在旧后端只造 handle 不发送，靠 `NotificationHandle::drop` 以 `asynchronous:true` 补发 —— 所以通知能弹出。
- **点击上报的前提（反直觉，防后人误删）**：无 action 按钮的通知 `needs_response()=false` → 发送后 ≤2s 清 pending map → 之后点击被系统丢弃（静默 no-op，测试全绿也测不出）。必须：Rust 注册 ActionType（`cnbBuildOpen`，Action "open"/「打开」）+ 前端 `sendNotification` 恒带 `actionTypeId`。本体点击报 `tap`、按钮报 `open`。
- 注册 on_action 后发送路径切到 show_tracked→wait()：无按钮立即返回，有按钮才阻塞；自动消失由 notify.m 0.5s poll timer 兜底，线程不泄漏。
- JS 包 2.7.0 **没有** onAction/registerActionTypes 导出，点击只能走 Rust `on_action` → `emit("cnb://build-notification-action")` → 前端 listen（事件名 `//` 合法，Tauri 2 校验 = 字母数字/`-`/`/`/`:`/`_`）。
- payload 用 `extra` 传 repoPath/sn（经 ActiveNotification.extra 回到 Rust，比 id 映射可靠）。

## QA 抓到的教训
- 第一轮 FAIL：功能「实现正确但机制失效」—— 测试全绿、typecheck/lint/build 全过，但 macOS 点击整链路静默 no-op。结论：**涉及 OS 桥接的功能，源码级证据链审查不可省**。
- eslint 在本环境直跑 exit=2 是 EPIPE 环境假失败，用 `--output-file` 前台重跑取真实码。
- madge 查循环依赖在本机沙箱 OOM，用手工追踪替代。
