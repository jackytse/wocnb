## 托盘面板滚动条修复（7e99ca7）

- 现象：面板列表超长时无滚动条。**根因是 CSS 层叠层级**：main.css 顶部 `* { scrollbar-width: none }` / `*::-webkit-scrollbar{display:none}` 是未分层（unlayered）规则，Tailwind 工具类在 @layer utilities 里 —— 未分层规则恒优先于任何 @layer 规则（与选择器优先级无关），所以 `[&::-webkit-scrollbar]:block`、`[scrollbar-width:auto]` 等任意变体全部失效。实测：计算值恒 none、scrollbar 占位 0px。
- 修复：main.css 追加未分层规则 + `[data-tray-scroll]` 属性选择器（scrollbar-width:auto + ::-webkit-scrollbar 8px + 透明边框 + background-clip:content-box 做 4px 悬浮滑块，深浅两套）；TrayPanel 滚动容器改用 `data-tray-scroll` 属性。
- **重要经验（通用）**：在 Tailwind v4 项目里要覆盖 main.css 这类未分层全局规则，必须同样写在未分层位置（或内联 style），Tailwind 任意变体一律打不过；验证手法用 headless Chrome iframe + `offsetWidth-clientWidth`（经典滚动条占 8px），别只看截图（headless 可能不画滚动条）。
- 另：托盘面板 localStorage 种子数据 time 必须是 ISO 字符串（useRecentRepos 校验），数字时间戳会被整体过滤成空列表。

- 用户报同样报错且确认版本实际已删除 → deletePackage/deletePackageTag 走了 cnbFetch；swagger 确认两个 DELETE 端点 200 响应体为空 → 改 cnbFetchVoid。
- **教训升级（同日 2 例）**：新写端点接入时必须逐个核对 swagger 的 200 响应 schema —— "OK"/空 schema 一律 cnbFetchVoid；建议后续可考虑给 cnbFetch 加「2xx + 空 body 且 T 类型可空」的兜底，或在 code review 清单固化此项。

## cnbFetch 空 body 系统性兜底（同日第 3 例后根治）

- 审计方法：脚本扫描全部 74 个写调用块 × swagger 200/201 响应 schema 交叉比对。**发现 swagger 双向不可靠**：POST /-/git/tags 等声明空 schema 但实际有 body（注释与线上行为证实）；POST /user 等实际空 body。逐端点换 cnbFetchVoid 无法根治。
- **根治方案**：cnbFetch 先 response.text()——空白体（trim 后为空，含纯换行）返回 undefined；非空 JSON.parse（解析错误照抛 + console.error 带 body 片段）。一处保护全部调用点与未来端点。
- 配套加固：normalizePull / normalizeRelease 改可选参数（原 raw.number 直接取字段会 TypeError）；其余 normalize* 审计已容忍 undefined。
- 新增端点接入时不再需要纠结通道选择：返回值用到才解析，空体天然安全；cnbFetchVoid 仍用于「明确空 body」场景（语义清晰）。

## 空仓库引导态（修复永久骨架 + 提交页签误报 404）

- 根因：空仓库 head 404（"branch main not found"）→ effectiveRef 空 → 代码页签永远渲染骨架；提交页签空 ref 请求 → 404 误报「资源不存在」。
- 判定：detail 已加载 + 无 ref + headError.kind==='notFound' → repoUninitialized；网络错误不算（错误态+重试）。
- 新组件 RepoEmptyRepo（标题/说明/可复制推送命令/浏览器打开），代码+提交页签共用。
- **空仓库 API 实测口径**：head=404 branch main not found；contents=200 {"type":"empty"}；branches=[]；git remote = https://cnb.cool/{path}.git，默认分支 main。

## fork 仓库同步上游更新（fc2e4b9）

- **OpenAPI 无原生 fork 同步端点**（swagger + cnb CLI 双确认）。网页端「同步更新」（官方公众号确认存在）走内部接口未公开；fork 与上游 git 对象库互不可达（fork 内引用上游 SHA → 404 not found），PR 不支持跨仓库 head（invalid commit revision）。分支创建 POST /-/git/branches 支持 {name, start_point}（SHA），但对象库隔离使同步无法在 API 层拼接。
- **根治方案：StartBuild 动态注入流水线**。POST /{repo}/-/build/start 的 dto.StartBuildReq 有 `config` 字段（YAML 字符串）——注入 api_trigger 流水线执行 git fetch upstream + merge + push；**构建环境 checkout fork 时已内置 upstream remote**（首次实测 git remote add 报 "remote upstream already exists" 中断，须 set-url 兜底），CNB_TOKEN 自带本仓库推送权限。端到端实测：hello-cnb fork 落后 8 提交 → 一次构建全量合入。
- **网页 API 逆向方法论**：CDN chunk（cnb.cdn-go.cn/_next/static/chunks/）grep url: 模板可拿到网页真实端点（如 /-/build/start/deploy）；但 api 模块常在异步 chunk 中难定位。swagger 缺 schema 时（{} 空 body），实测报错文案可反推必填字段（title length / invalid Git Refspec 等）。
- UI：RepoForkSyncBar 琥珀提示条（仅 fork 且 SHA 不一致渲染）+ 确认弹窗 + toast 查看构建；检测失败（unknown）静默不显示。UButton 无 amber 色，用 warning。

## AI 用量 404 语义定案（2026-11-20）

- 定案：ai-audit/ai-request 对无 AI 用量的构建返回 404 是**常态**（用量只统计流水线中 NPC/AI 能力的消耗，普通 CI 构建必然无记录）。UI 按**空态**展示（「本次构建无 AI 用量记录」+ 原因说明），不再是中性「数据不可用」+ 重试。
- 坑复现：i18n 消息值要含 `{'@'}`，TS 源码里必须写成 `{\'@\'}`（引号在值内）——写错顺序成 `{'\'@'\'}` 会让裸 `'` 提前闭合字符串，vue-tsc 报 Invalid character 且 locales 编译测试抓 Invalid linked format，两层都能拦。
- 验证手段受限：本地令牌（用户给的 f5yA...）缺 repo-cnb-trigger/history scope，无法真机验证 ai-audit 的 pipelineId 口径；若用户有 NPC 构建仍需真机确认。
