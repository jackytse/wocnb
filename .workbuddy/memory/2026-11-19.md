## 标签（label）配色修复 + rc.34 发版（提交 f438901 / e9c171d，tag v0.1.0-rc.34）

- **现象**：首页「我创建的」列表里，Issue 标签渲染成一块近乎空白的浅色方块，字看不见（用户截图反馈"标签颜色很奇怪"）。
- **根因（实测 API 确认）**：CNB `GET /user/issues` 返回的 `label.color` 是 **#E5F5FF、#FCEEE8 这类极浅粉彩**（H 高饱和 + L≈95%）。旧实现两种写法都错：
  - 首页 `HomeIssueList.vue`：`variant="subtle"` + `color: label.color` → 近白字压近白底；
  - 仓库页（IssueList / IssueDetail / PullList）：`color: label.color` + `backgroundColor: ${color}1a` → 白底上叠 10% 同色 ≈ #FBFDFF，同样看不见。
  - PR 详情是「中性徽标 + 色圆点」，圆点同样接近白色，看不出颜色。
- **修复**：
  - 新增 `src/utils/labelColor.ts`：`normalizeLabelColor`（3/4/6/8 位十六进制、去 #、非法返回 null）、`relativeLuminance` / `contrastRatio`（WCAG，注意必须做 gamma 反变换）、`readableTextColor`、`labelChipStyle`。
  - 前景色策略：浅底（相对亮度 ≥0.5）→ **同色相压暗 + 饱和度×2.2**，从 L=0.38 每档降 0.04 取第一个 ≥4.5:1 的候选（#E5F5FF → #006bad、#FCEEE8 → #c23a00，保留色相关联）；中深色底 → 白 / #111827 / #000 依序取第一个达标者（#ff0000 只有纯黑能过 5.25:1；#111827 是 4.44、白是 3.96）。
  - 底色用**标签色本身（不透明）**，因此明暗主题下表现一致，不需要主题分支；配 `inset 0 0 0 1px rgba(0,0,0,.08)` 内描边（用 border 会改变盒高，同行徽标会高低不齐）。
  - 新增 `components/LabelChip.vue` 作为标签唯一出口（无可用颜色时回落中性徽标），5 处调用点全部收敛（首页 / 仓库 Issue 列表 / Issue 详情 / PR 列表 / PR 详情）。
- **测试**：新增 `src/utils/__tests__/labelColor.test.ts` 13 例，把「对比度 ≥ 4.5:1」写成断言（真实色值 #E5F5FF、#FCEEE8 做了回归）；全量 44 文件 **704** 用例全绿，typecheck / lint / build 通过。
- **发版**：rc.34，ci-main `cnb-71t-1k7ol4nil` 全绿；tag 构建 `cnb-lm4-1k7ol76qn` 三条流水线全绿（meta 57s / macos 72s / windows 96s，rust toolchain 缓存已热，不再全量重编），Release 7 个附件齐全、prerelease=true。
- **观察项（未改，待用户决定）**：所有页面的 UTabs 都是 `color="neutral"` + pill，Nuxt UI v4 的 neutral 选中态是 `bg-inverted` → 浅色主题下是一块纯黑药丸（截图里"我创建的"就是），与整体浅色 UI 反差很大。若要改需要统一覆盖 tabs 主题或加一层 AppTabs 包装，属全局视觉变更，没在这次一并动。

## 应用内热更新（macOS，tauri-plugin-updater）落地（提交 801e054）

- **决策（用户拍板）**：macOS 先行（Windows 节点 makensis 起不来，rc 只出裸 exe，更新器必须依赖 NSIS/MSI 安装器产物 → 无法自更新）；签名私钥走 **CNB 密钥仓库**（用户需亲自创建仓库，token 缺 group-resource:rw 不能代建）。
- **端点设计（关键）**：CNB 的 `-/raw/main/xxx` 返回 HTML 不是纯文件 → 清单不能用仓库文件。改用**固定 tag `updater-manifest` 的 Release**承载 `latest.json` 附件（附件 `-/releases/download/<tag>/<name>` 匿名可下、URL 永不变）。该 tag+Release 已一次性创建（Release id 2123227794871676928）；每次发版由 release-macos 新增的 publish-manifest 阶段 `CNB_BRANCH=updater-manifest bash release-upload.sh release/latest.json` 覆盖上传（overwrite:true）。
- **配置分层**：主 `tauri.conf.json` 只放 `plugins.updater`（endpoints + pubkey + windows.installMode=passive），`createUpdaterArtifacts: true` 放在**覆盖层** `src-tauri/tauri.updater.conf.json`，CI build 加 `--config src-tauri/tauri.updater.conf.json` 才开启 —— 本地 `pnpm tauri build`（无私钥）不受影响。清单端点：`https://cnb.cool/jackytse/wocnb/-/releases/download/updater-manifest/latest.json`。
- **签名私钥双来源**：① `.cnb.yml` release-macos 顶层 `imports: https://cnb.cool/jackytse/secrets/-/blob/main/wocnb/tauri-updater.yml`（**该仓库尚不存在，必须由用户先建，否则 release-macos 流水线会因 imports 拉取失败而失败**）；② 构建机文件回退 `~/.tauri/wocnb-updater.key`（TAURI_SIGNING_PRIVATE_KEY 允许传路径）。两层都缺 → build 阶段明确报错退出。导入文件已预生成在 `~/.tauri/wocnb-updater.imports.yml`（key 无密码，`TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ""` 必须显式置空防 CI 卡交互输入）。
- **热更新产物**：`createUpdaterArtifacts=true` 时 macOS 更新包是 `bundle/macos/WOCNB.app.tar.gz`（不是 dmg 目录）+ `.sig`；新脚本 `collect-updater-macos.sh` 收集重命名为 `wocnb-<版本>-macos-arm64.app.tar.gz[.sig]` 并用 python3 生成 latest.json（version/notes/pub_date UTC/platforms.darwin-aarch64.signature+url）。url 指向 `v<版本>` tag 的 Release 附件。
- **前端**：`installUpdate()`（updater check → **通道校验**：update.version 必须等于当前通道检测出的 latestVersion，不等 → mismatch 拒装，防 release 通道被清单里的 rc 绕过 → downloadAndInstall 进度回填 → ready）+ `relaunchApp()`（plugin-process，用户手动点「重启完成更新」，不自动杀进程）。about 页「一键更新」按钮三态（初始/下载中带百分比/ready 重启），失败展示原文 + 「前往下载」兜底。
- **坑**：清单不含 windows 条目 → Windows check() 抛错 → failed 分支即"手动下载引导"，是预期行为不是 bug；`installStatus` 在 setUpdateChannel 时也要复位（旧通道安装态会污染新通道界面）。
- **验证**：44 文件 **713** 用例全绿（新增 9 例）；cargo check/cargo test 通过；ci-main `cnb-5m3-1k7on716t` 全绿。
- **生效边界**：rc.34 及以前无 updater → 仍手动下载；**首个可热更新的版本是下一次发版（rc.35）**，且 rc.35 必须在密钥仓库就绪后打 tag（否则 mac 流水线失败、Release 缺 dmg）。
