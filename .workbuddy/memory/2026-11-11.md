## 成员页「外部贡献者」400 修复（2026-11-11，主理人直接定位）

- 现象：成员菜单 → 外部贡献者页签，页面红字「加载失败 CNB API 请求失败: 400，服务器返回：This feature is not supported for organizations.」
- 根因：`GET /{slug}/-/outside-collaborators` 在 swagger 里明确是**仓库级**端点（scope `repo-manage:r`，描述「查询指定仓库的外部贡献者」），members.vue 却传了 `selectedGroup.path`（组织路径）。外部贡献者=「不属于组织成员但拥有某仓库特定权限」的仓库侧概念，组织实体上不存在该关系，网关直接 400。
- 修复：outsiders 页签先 `fetchCnbGroupRepos(slug,1,100)` 拉组织仓库 → `USelect` 仓库选择器（query.repo 深链，默认首个仓库）→ 用 `组织/仓库` 完整路径请求贡献者。组织下无仓库 → 引导空态；仓库列表 403/网络 → 页签内错误 + 重试；服务端仍返回该 400 → 引导态（UAlert）而非红色错误。
- 顺带修路径编码：新增 `encodeSlugPath`（逐段 encodeURIComponent 保留 `/`）。原 `encodeURIComponent(slug)` 会把 `a/b` 压成 `a%2Fb`，多级子组织/仓库路径都会路由错。
- 数据层：useCnbMembers 导出 `encodeSlugPath` / `isOutsideCollaboratorsUnsupported`（大小写不敏感匹配服务端固定 errmsg）；fetchOutsideCollaborators 形参改名 repoPath。
- i18n 三语 +11 键（outsiders* / searchOutsidersPlaceholder）。设计文档 §5 members 行补勘误块。
- 验证：新增 useCnbMembers.test.ts（12 例）→ 276 vitest 全绿；typecheck/lint/build 零错误。
- 长期约定：**CNB 外部贡献者只能按仓库查，任何"组织维度"入口必须先落到仓库**。

## 组织能力扩展（第二轮，2026-11-11，团队 org-features）

用户反馈「组织相关功能太少」，对照 swagger 全量补齐组织域治理能力。组织域共 46 个端点，此前仅用 10 个。

### 交付

- **新增数据层**：`useCnbOrgSettings.ts`(497) / `useCnbBranchProtections.ts`(382) / `CreateGroupModal.vue`(269) / `OrgSettingsTab.vue`(890) / `OrgProtectionsTab.vue`(694)。
- **成员写操作**：`useCnbMembers.ts` 159→457，`members.vue` 722→1321。添加/改角色/移除 + 批量权限（降级逐人）+ 外部贡献者改角色/移除。
- **创建组织站内化**：GroupsMenu 的「创建组织」不再外跳 cnb.cool；组织页右上角「新建子组织」（path 前缀锁定父组织）。

- 测试 345 例（+~80：33 成员 / 26 设置 / 19 保护分支 / 2 概览映射 + 1 消息编译），三语各 +约 160 键。

### 关键事实修正（**别再信旧结论**）
- **`GET /{group}` 的 200 schema 是 `dto.OrganizationAccess`**，含 `access_role`（用户在该资源的最大权限）以及 `description/site/email/domain/remark/wechat_mp/readme_repo_path` 全部 7 个可编辑字段。此前设计文档写「不返回 access_role / email / domain…」是错结论，直接导致下钻子组织时角色被硬编码空串 → canManage 恒 false → **子组织三个页签全只读**（QA 抓到的 P1）。
- 子组织**只能**通过 `?slug=` 下钻到达（GroupsMenu 只列顶层组织），所以上面那条等于「子组织在桌面端不可治理」。已修 + 单测锁定（`useCnbOrg.test.ts` 的 accessRole 映射用例）。
- 保护分支是 **22 字段**（id + rule + 21 可写），非 26；`organization.SettingValue` 是 **33 个**枚举，非 34。

### 关键陷阱（写进代码注释）
- **空 body 写端点必须用 `cnbFetchVoid`**：CNB 的 POST/PUT/DELETE 多数返回 200 + 空 body，`cnbFetch` 会在 `response.json()` 抛 "Unexpected end of JSON input"，把成功报成失败，用户反复点击。
- **vue-i18n 的 `@` 陷阱**：文案里字面量 `@`（邮箱占位符、可 @NPC）会被当 linked message 起始符，**渲染时**抛 `Invalid linked format`，而 typecheck/键一致性/构建全不报错。用 `{'@'}` 转义或换词。已加常驻用例（`locales.test.ts` 的「消息可编译」，遍历三语全部消息编译，负向验证过有效）。
- **切组织清 slug 不能复用 buildQuery**：它会把旧 slug 原样写回，`router.replace` 变 no-op（URL 与状态不一致）。

### 不做项（已裁决，勿重开）
- 上传组织 Logo：`upload_url` 域名服务端动态下发 + 需 PUT 二进制流，撞附件上传同一堵墙 → 仅外跳
- 删除组织：需 `x-cnb-identity-ticket`（微信扫码二次验证）→ 仅外跳
- 贡献者趋势 `/{slug}/-/contributor/trend`：scope 是 `repo-code:r`、语义是仓库，组织路径会 400
